## 1. Что где лежит

```
prac_linal/
├── CONTRIBUTING.md     ← ты здесь
├── COURSE.md           правила зачёта, дедлайны, требования к отчёту (прочитать!)
├── tasks/              методички PLA_LAB1..6_2025.pdf
├── lectures/           ссылки на лекции + доп. материал
├── template/
│   ├── plotstyle.py    единый стиль графиков — подключают все
│   ├── report.tex      шаблон отчёта (трогает только сборщик)
│   └── build.sh        сборка PDF
└── labs/lab0N/
    ├── README.md       чек-лист сдачи, контрольные вопросы, грабли, РАСПРЕДЕЛЕНИЕ
    ├── draft.md        общее: исходные данные, введение, заключение
    ├── draft_A.md      черновик блока A  ─┐
    ├── draft_B.md      черновик блока B   ├ каждый пишет ТОЛЬКО свой файл
    ├── draft_C.md      черновик блока C  ─┘
    ├── code/           common.py (общий) + block_a.py / block_b.py / block_c.py
    ├── figures/        картинки в PDF — их создаёт код, руками не кладём
    └── report/         report.tex и report.pdf — собирает сборщик
```

## 2. Главное правило: у каждого свои файлы

Конфликты в git возникают, когда двое правят один файл. Поэтому:

| Кто | Пишет | Не трогает |
|---|---|---|
| A | `draft_A.md`, `code/block_a.py`, `figures/p01…` из своих пунктов | чужие draft/block |
| B | `draft_B.md`, `code/block_b.py` | чужие draft/block |
| C | `draft_C.md`, `code/block_c.py`, **`code/common.py`** | чужие draft/block |
| Сборщик | `draft.md`, `report/` | — |

Нашёл ошибку у соседа — не правь сам, напиши ему (или комментарий в GitHub).
Нужно поменять `common.py` — через Ивана.

## 3. Установка (один раз)

1. Прими приглашение в репозиторий (придёт на почту GitHub или в https://github.com/notifications).
2. Склонируй:
   ```bash
   git clone https://github.com/aloneek/prac_linal.git
   cd prac_linal
   ```
   Удобнее всего в VS Code: `Cmd/Ctrl+Shift+P` → `Git: Clone` → вставить ссылку.
3. Python 3.10+ и библиотеки:
   ```bash
   pip install numpy matplotlib
   ```
4. **LaTeX ставить не нужно.** PDF собирает сборщик (см. раздел 6).

## 4. Ежедневный цикл (4 команды)

```bash
git pull                      # 1. ВСЕГДА перед началом работы
# ... работаешь в своих файлах ...
git add labs/lab02/draft_B.md labs/lab02/code/block_b.py labs/lab02/figures
git commit -m "ЛР2 блок B: пункты 6-8"
git pull --rebase             # 3. подтянуть то, что успели запушить другие
git push                      # 4. отправить
```

- Коммить часто и маленькими кусками — «сделал пункт → коммит → пуш».
  Так соседи видят прогресс, а сборщик не ждёт до последней ночи.
- Сообщение коммита — по-русски, что сделано: `ЛР2 блок A: пункт 5, вывод общего класса`.
- В VS Code всё то же самое делается кнопками во вкладке Source Control (третья иконка слева).
- Если `git pull` ругается на конфликт — ничего не удаляй, напиши в чат, разберём.

## 5. Как писать черновик (`draft_X.md`)

Пишешь обычный Markdown. Сборщик превратит его в LaTeX, поэтому придерживайся формата:

**Формулы** — LaTeX внутри долларов: `$\det A = ad - bc$` в строке,
отдельной строкой — между `$$ ... $$`. Матрицы:
```
$$
A = \begin{pmatrix} 0 & -1 \\ 1 & 0 \end{pmatrix}
$$
```

**Структура каждого пункта** (одинаковая у всех — так отчёт выглядит цельным):
```markdown
## Пункт 6. Прямая y = 0 → y = ax, прямая x = 0 → y = bx

**Общий класс.** Рассуждение и вывод: какие матрицы вообще подходят и почему.

**Выбранная матрица.** $$ A = ... $$

**Визуализация.** Результат показан на рисунке p06.
![Отображение пункта 6: исходный и отображённый многоугольник](figures/p06.pdf)

**Анализ (задание 2).** Собственные числа/векторы, det, ядро/образ — то,
что требуется для этого пункта. С расчётом руками, а не только ответ numpy.

**Вывод.** Почему получилось именно так. Не «мы построили», а «det < 0,
потому что отражение меняет ориентацию».
```

**Рисунки.** Имя файла = номер пункта: `p06.pdf`; для пунктов 15/16 — `p15_A.pdf`, `p15_B.pdf`,
`p15_AB.pdf`, `p15_BA.pdf`. В тексте ссылайся как «на рисунке p06» — сборщик заменит
на «рисунке 6» с правильной нумерацией. Подпись в `![...]` — полным предложением.

**Числа** — 2–3 знака после запятой, не 15 из numpy. Удобно: `np.set_printoptions(precision=3, suppress=True)`.

## 6. Как из этого получается PDF (что делает сборщик)

```
draft.md + draft_A.md + draft_B.md + draft_C.md      figures/*.pdf
                     │                                     │
                     ▼                                     │
     сборщик (Альберт + Claude) переводит Markdown         │
     в report/report.tex по шаблону template/report.tex ◄──┘
                     │
                     ▼
     ./template/build.sh 2  →  xelatex дважды  →  report/report.pdf
                     │
                     ▼
     git push → все открывают report.pdf на GitHub и вычитывают
```

- Шаблон оформлен по ГОСТ 7.32: титульник, содержание, нумерация рисунков и формул,
  подписи, поля, код в приложении — это всё делает шаблон, вам об этом думать не надо.
- Из каждого `draft_X.md` части про «Анализ (задание 2)» переезжают в раздел «Задание 2»
  отчёта — поэтому важно, чтобы этот подзаголовок был у каждого пункта.
- Код из `code/` автоматически попадает в приложение — пиши его читаемо, с комментариями.
- Claude **только** переводит в LaTeX и проверяет оформление. Решения, выводы и формулы —
  ваши. Чего нет в черновике, того не будет в отчёте.

Хочешь собрать сам: нужен TeX Live/MacTeX с `xelatex` и шрифт Liberation Serif;
потом `./template/build.sh 2`. Не обязательно.

## 7. Код

- Общая часть лабы — в `code/common.py`: исходные данные (a, b, c, d, многоугольник)
  и функция визуализации. **Свои копии чисел не заводить** — только `from common import ...`.
- Свой блок — в `code/block_X.py`, запускается из папки `code/`:
  ```bash
  cd labs/lab02/code && python block_b.py
  ```
  Картинки сохраняются в `../figures/` через `save()` из `template/plotstyle.py`.
- Перед пушем: файл запускается с нуля без ошибок и пересоздаёт все свои картинки.

## 8. Ревью по кругу

A проверяет B, B проверяет C, C проверяет A. Проверить = прочитать черновик соседа,
пересчитать руками хотя бы одну матрицу и собственные числа, задать вопросы.
Это не формальность: **тест на защите индивидуальный и по всей работе**, а не по своему блоку.
Ревью — самый дешёвый способ разобраться в чужих пунктах.

## 9. Про ИИ

Курс прямо засчитывает «неосознанное списывание результатов ИИ» как списывание.
Спрашивать ИИ объяснения теории — можно и полезно. Вставлять в черновик то, что
не можешь объяснить сам, — нельзя: на тесте это всплывёт у того, кто вставил.

## Шпаргалка

```bash
git pull                                   # перед работой
git add <свои файлы> && git commit -m "…"  # сделал кусок
git pull --rebase && git push              # отправил
```
Черновик → `draft_X.md` · код → `code/block_x.py` · картинки → `figures/pNN.pdf` ·
формулы → `$…$` · у каждого пункта есть «Анализ (задание 2)» и «Вывод».
